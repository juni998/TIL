## 클래스 로더 (Class Loader)

</summary>

### 클래스 로더가 왜 필요한가?
Java 코드를 작성하고 `javac`로 컴파일하면 `.class`파일이 생긴다. 그런데 이 파일은 그냥 디스크 위에 있는 파일이다.
JVM이 이 파일을 실제로 **메모리에 올려서 실행 가능한 상태**로 만들어야 비로소 프로그램이 돌아간다.
<br>
이 역할을 하는 게 바로 **클래스 로더**이다.

> 디스크에 있는 `.class`파일을 JVM 메모리(런타임 데이터 영역)로 가져오는 배달부 역할

### 클래스 로더의 3단계 과정

### 1. 로딩 (Loading) - 파일을 찾아서 읽어라
클랫 로더가 `.class`파일을 찾아 바이트 코드로 읽고, 메서드 영역에 기본 정보를 저장하는 단계

<br>

이때 클래스 로더는 **3계층 구조**로 되어있다.
1. Bootstrap ClassLoader - `java.lang.String` 같은 JDK 핵심 클래스 담당
2. Extension ClassLoader - `javax.*` 등 확장 라이브러리 담당
3. Application ClassLoader - 내가 만든 클래스, 외부 라이브러리 담당
   
<br>

로딩 할 때 **항상 위 계층에 먼저 물어본다.** 이를 **부모 위임 모델(Parent Delegation Model)** 이라고 한다.

<br>

예를 들어 `String` 클래스를 로딩할 때, Application -> Extension -> Bootstrap 순으로 위임해서 결국 Bootstrap이 처리한다.
덕분에 누군가 악의적으로 `java.lang.String`을 가짜로 만들어도 교체가 불가능하며 **보안상 매우 중요한 설계**이다.

### 2. 링킹 (Linking) - 로딩한 클래스를 검증하고 준비하라
링킹은 세 단계로 나뉜다.
#### 검증 (Verify)
"이 바이트 코드가 JVM 스펙에 맞게 올바르게 작성됐는가?" 를 검사한다. 손상된 파일이나 악의적으로 조작된 `.class` 파일을 걸러낸다.

#### 준비 (Prepare)
`static` 변수들에 기본 값을 할당한다. 아직 실제 값이 들어가는 것은 아니다.
``` java
static int count = 100;
// 준비 단계 : count = 0 (기본 값)
// 실제 값은 초기화 단계에서 대입
```

#### 분석 (Resolve)
클래스 파일 안의 심볼릭 참조를 실제 메모리 주소로 바꾼다.
예를 들어 `"java/lang/String"` 이라는 텍스트로 저장된 참조를 실제 메모리 주소로 연결하는 작업

### 3. 초기화 (Initialization) - 진짜 값을 넣어라
`static` 변수에 실제 값이 대입되고, `static` 블록이 실행되는 단계이다.

``` java
public class Counter {
    static int count = 100;       // 여기서 100이 실제로 대입됨

    static {
        System.out.println("Counter 클래스 초기화!"); // 여기도 실행됨
    }
}
```

초기화는 **처음 사용될 때 딱 한 번만 실행**된다. 이미 초기화된 클래스는 다시 초기화하지 않는다.


### 전체 흐름 정리

```
.class 파일
    ↓
① 로딩    → 바이트코드를 메모리에 올림 (메서드 영역)
    ↓
② 링킹
   - 검증  → 바이트코드 유효성 검사
   - 준비  → static 변수에 기본값 (0, null, false)
   - 분석  → 심볼릭 참조 → 실제 주소
    ↓
③ 초기화  → static 변수에 실제 값 대입, static 블록 실행
    ↓
 실행 가능 상태
```

## 런타임 데이터 영역 (Runtime Data Areas)

</summary>

### 런타임 데이터 영역이란?
클래스 로더가 `.class`파일을 메모리에 올렸는데 그 메모리가 바로 **런타임 데이터 영역**이다.
> JVM이 프로그램을 실행하는 동안 사용하는 작업 공간 전체

### 런타임 영역의 5가지 영역
#### 영역의 구분
반드시 알아야 할 구분!

구분|해당 영역|의미|
|--|--|--|
|모든 스레드가 공유|메서드, 힙 영역| 어느 스레드에서든 접근 가능|
|스레드마다 별도 생성|JVM 스택, PC 레지스터, 네이티브 메서드 스택| 스레드 하나당 하나씩 존재|
<br>

이 구분을 알아야 하는 이유는 공유 영역에서 **동시성 문제(race condition)** 가 발생하기 때문이다.

#### 1. 메서드 영역 (Method Area) - 클래스 정보를 보관하는 도서관
클래스 로더가 로딩한 클래스의 정보를 보관하는 공간, 스태틱 영역 이라고도 부른다. 저장되는 목록은 다음과 같다
- 클래스 이름, 부모 클랙스 이름
- 메서드 바이트 코드
- `static` 변수
- 상수 풀 (문자열 리터럴, 상수 값 등)

#### 2. 힙 영역 (Heap) - 객체들이 살아가는 아파트 단지
`new` 키워드로 생성한 객체 인스턴트와 배열이 저장되는 공간. 가장 큰 메모리 영역이고, 
**가비지 컬렉터(GC)**가 관리하는 영역이기도 하다.
<br>

힙의 내부
```
   힙 (Heap)
   ├── Young Generation  ← 새로 생성된 객체
   │   ├── Eden          ← 객체가 처음 태어나는 곳
   │   ├── Survivor 0    ← GC에서 살아남은 객체
   │   └── Survivor 1    ← GC에서 살아남은 객체
   └── Old Generation    ← 오래 살아남은 객체
```

객체의 생애주기를 따라가보면 다음과 같다.
1. `new Person()` -> Eden에 생성
2. Minor GC 발생 -> 살아남으면 Survivor로 이동
3. Survivor를 여러 번 오가며 살아남으면 -> Old Generation으로 이동
4. Old generation도 꽉 차면 -> Major GC(Full GC) 발생

> 힙은 모든 스레드가 공유하기 때문에, 여러 스레드가 동시에 같은 객체를 수정하면 문제가 생긴다.
> 이것이 `synchronized`, `volatile`이 필요한 이유이다.

#### 3. JVM 스택 (JVM Stack) - 메서드 호출을 기록하는 콜스택 메모장
메서드가 호출될 때마다 **스택 프레임(Stack Frame)**이 하나씩 쌓이고, 메서드가 끝나면 사라진다.
스레드마다 독립적으로 존재한다.

스택 프레임 하나에는 아래와 같은 것들이 있다.
- 지역 변수 배열 - 메서드 안에서 선언한 변수들
- 피연산자 스택 - 연산 중간 결과를 임시 저장
- 프레임 데이터 - 메서드 반환 주소 등

코드로 보면 다음과 같다.
``` java
public static void main(String[] args) {
    int result = add(3, 5);  // ← add() 호출 시 프레임 추가
}

public static int add(int a, int b) {
    return a + b;  // ← 반환 시 프레임 제거
}

`스택 상태
┌──────────────┐
│  add 프레임   │  ← add() 호출되면 추가
│  a=3, b=5    │
├──────────────┤
│  main 프레임  │  ← 처음부터 있음
│  result=?    │
└──────────────┘`

```

여기서 중요한 오류가 바로 `StackOverflowError`이다. 재귀 호출이 무한히 반복되면 스택 프레임이 계속 쌓여 스택 공간이 꽉 차버린다.

``` java
public static void infinite() {
    infinite();  // 무한 재귀 → StackOverflowError!
}
```

#### 4. PC레지스터 (PC Register) - 지금 어디까지 읽엇는지 표시하는 책갈피
현재 스레드가 실행 중인 JVM 명령어의 주소를 저장한다. 스레드마다 독립적으로 존재한다.
<br>
CPU는 여러 스레드를 아주 빠르게 번갈아 실행한다. 스레드가 잠깐 멈췄다가 다시 실행될 때 "어디서 부터 이어서 실행해야 하지?" 를 알기 위해 PC 레지스터가 필요하다.

> 네이티브 메서드를 실행 중일 때는 PC 레지스터 값이 `undefined` 이다. 네이티브 메서드는 JVM이 아닌 OS에서 직접 실행되기 때문이다.

#### 5. 네이티브 메서드 스택 (Native Method Stack) - 자바 밖 세계와 연걸되는 통로
Java가 아닌 C/C++ 로 작성된 네이티브 메서드를 실행할 때 사용하는 스택이다. JNI(Java Native Interface)를 통해 호출된다.
<br>
대표적인 예시로는 `Thread.sleep()`,  `System.currentTimeMillis()` 같은 메서드들이 내부적으로 네이티브 메서드를 호출한다.

#### 전체 그림 정리

```
런타임 데이터 영역
│
├── [모든 스레드 공유]
│   ├── 메서드 영역  → 클래스 정보, static 변수, 상수 풀
│   └── 힙          → 객체 인스턴스, 배열 (GC 관리)
│
└── [스레드별 독립]
    ├── JVM 스택           → 스택 프레임 (지역변수, 연산)
    ├── PC 레지스터         → 현재 실행 명령어 주소
    └── 네이티브 메서드 스택 → C/C++ 네이티브 메서드 실행
```

## 실행 엔진 (Execution Engine)

</summary>

### 실행 엔진이 왜 필요한가?
지금까지의 흐름은
1. 클래스 로더가 `.class` 파일을 메모리에 올렸고
2. 런타임 데이터 영역에서 클래스 정보, 객체, 지역변수 등이 저장 됐다.
그런데 메모리에 올라간 바이트 코드는 아직 실행된 게 아니다. CPU는 바이트 코드를 직접 이해하지 못하며
CPU는 오직 기계어(네이티브 코드) 만 이해한다. 그래서 필요한게 바로 **실행 엔진**이다.

> 런타임 데이터 영역에 올라온 바이트 코드를 CPU가 이해할 수 있는 기계어로 변환해서 실행하는 역할

### 실행 엔진의 세 가지 구성
- 인터프리터 (Interpreter)
- JIT 컴파일러 (Just-In-Time Compiler)
- 가비지 컬렉터 (Garbage Collector)

#### 1. 인터프리터 (Interpreter) - 바이트 코드를 한 줄씩 번역하는 동시 통역사
바이트 코드를 한 줄씩 읽고, 해석하고, 실행 한다. 예시는 다음과 같다
```
바이트 코드 명령어 1 -> 기계어 변환 -> 실행
바이트 코드 명령어 2 -> 기계어 변환 -> 실행
바이트 코드 명령어 3 -> 기계어 변환 -> 실행
```

장점 : 처음 실행할 때 바로 시작할 수 있고, 별도의 준비 시간이 없다.
단점 : 같은 코드가 반복 실행될 때도 매번 새로 번역하기에 비효율적이다.

예시
```java
for (int i = 0; i < 10000; i++) {
    System.out.println("안녕하세요");
}
```

인터프리터는 `System.out.println()` 을 10,000번 매번 새로 해석하기에 굉장히 비효율적이다.
<br>
이 문제를 해결하기 위해 등장한 것이 바로 **JIT컴파일러** 이다.

#### 2. JIT컴파일러 (Just-In-Time Compiler) - 자주 쓰는 코드는 미리 번역해두는 전문 번역기
JIT컴파일러는 자주 반복 실행되는 코드(핫스팟)를 발견하면, 그 코드를 통째로 기계어로 컴파일해서 캐싱해둔다.
이후에는 번역 없이 캐싱된 기계어를 바로 실행한다.

```
처음 실행  → 인터프리터가 한 줄씩 실행
반복 감지  → JIT 컴파일러가 "이 코드 자주 쓰이네?" 감지
컴파일     → 해당 코드 전체를 기계어로 변환 후 캐싱
이후 실행  → 캐싱된 기계어를 바로 실행 (번역 과정 없음)
```

#### 인터프리터 vs JIT컴파일러
|구분|인터프리터|JIT컴파일러|
|--|--|--|
|번역 방식|한 줄씩| 코드 블록 전체|
|시작 속도|빠름 | 느림(컴파일 시간 필요)|
|반복 실행 속도| 느림| 빠름(캐싱된 기계어 사용)|
|메모리 사용| 적음 | 많음(캐싱 공간 필요)|

#### 핫스팟(HotSpot)이란?
JIT컴파일러는 자주 실행되는 코드만 골라서 컴파일한다. 이렇게 자주 실행되는 코드를 핫스팟(HotSpot)이라고 부른다.
<br>
JIT컴파일러는 핫스팟을 최적화할 때 여러 기법을 사용한다.
- 메서드 인라이닝 - 짧은 메서드를 호출 대신 코드 자체로 교체
- 루프 언롤링 - 반복문을 풀어서 분기 비용 제거
- 데드 코드 제거 - 실행되지 않는 코드를 컴파일에서 제외

#### 3. 가비지 컬렉터 (Garbage Collector / GC) - 힙에서 쓰레기를 치우는 청소부
힙 영역에서 더 이상 참조되지 않는 객체를 탐지하고 메모리를 회수하는 역할

#### GC의 핵심 개념 - Stop the World
GC가 실행되는 동안 GC 스레드를 제외한 모든 스레드가 멈춘다. 이를 Stop the World(STW) 라고 한다.
<br>

왜 멈춰야 할까? GC가 객체 참조를 정리하는 동안 다른 스레드가 객체를 생성하거나 수정하면 메모리 정합성이 깨지기 때문이다.

> STW 시간이 길면 애플리케이션이 그만큼 멈추는 것처럼 느껴진다. 그래서 GC 튜닝의 목표는 대부분 STW 시간을 최소화 하는 것

#### GC의 동작 원리 - Mark and Sweep
GC는 기본적으로 두 단계로 동작한다.
1. Mark - GC Root에서 시작해 참조 가능한 객체를 모두 표시
2. Sweep - 표시되지 않은 객체(쓰레기)를 메모리에서 제거
3. Compact - (선택적) 남은 객체를 한 쪽으로 모아 메모리 단편화 해소

GC Root란 참조의 시작점이다. JVM 스택의 지역 변수, `static`변수 등이 GC Root가 된다.

#### 전체 흐름 정리
```
바이트코드 (런타임 데이터 영역)
        ↓
   실행 엔진
   ├── 인터프리터   → 처음엔 한 줄씩 실행
   ├── JIT 컴파일러 → 핫스팟 감지 시 통째로 컴파일·캐싱
   └── 가비지 컬렉터 → 힙의 불필요한 객체 자동 수거
        ↓
    기계어 실행 (CPU)
```
