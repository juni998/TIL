## Tri-color Marking (삼색 마킹)
### 핵심 개념
> GC가 살아있는 객체를 찾기 위해 힙 전체를 그래프 탐색(DFS/BFS)하는 알고리즘
```
왜 "그래프" 인가?
  힙의 객체들은 서로 참조로 연결되어 있음

  UserService -> UserRepository -> DataSource -> Connection
  OrderService -> OrderRepository -> DataSource (공유!)

  이게 정확히 방향성 그래프(Driected Graph) 구조
  -> 그래프 탐색으로 살아있는 객체를 찾는 것이 Marking
```

### 세 가지 색깔의 정확한 의미
```
흰색 :
  아직 GC가 방문하지 않은 객체
  마킹 시작 시 모든 객체는 흰색
  마킹 완료 후 흰색으로 남은 것 = 수거 대상

회색 :
  GC가 발견했지만, 이 객체가 참조하는 자식들을 아직 처리 안함
  처리 대기 큐(Mark Stack)에 들어있는 상태
  회색 객체가 없어질 때까지 마킹 계속

검정 :
  이 객체와 이 객체의 모든 자식까지 처리 완료
  살아있음 확정
  재방문 불필요
```

### 동작 원리 (내부 구조)
#### 마킹 알고리즘 전체 흐름
```
STEP 1 : 초기화
  모든 객체 -> 흰색으로 초기화

STEP 2 : GC Root에서 시작
  GC Root가 참조하는 객체 -> 회색으로 표시
  Mark Stack에 추가

STEP 3 : 회색 객쳋 처리 (반복)
  1. Mark Stack에서 회색 객체 꺼냄
  2. 이 객체가 참조하는 자식들 확인
  3. 흰색 자식 -> 회색으로 변경, Mark Stack에 추가
  4. 현재 객체 -> 검정으로 변경
  5. Mark Stack이 빌 때까지 반복

STEP 4 : 마킹 완료
  흰색으로 남은 객체 = 아무도 참조하지 않음 -> 수거 대상

```

### 핵심 불변 조건 (Tri-color Invariant)
> 검정 객체는 흰색 객체를 직접 참조하면 안 된다.
Tri-color Marking이 올바르게 동작하기 위한 유일한 규칙!

```
왜 이 규칙이 중요한가?

검정 = 처리 완료 = 다시 보지 않음
흰색 = 수거 대상 후보

검정 -> 흰색 참조가 생기면 :
  흰색 객체는 사실 살아있음
  그러나 GC는 검정을 다시 안 봄
  -> 흰색을 수거 = 살아있는 객체 삭제

이 규칙이 깨지는 조건 :
  1. 검정 객체에 흰색 자식 참조 추가
  2. 그 흰색 객체로 가는 다른 모든 회색 경로 제거

두 조건이 동시에 만족될 때 문제 발생
```

### Tri-color Marking에서 회색에 필요한 이유?
회색은 처리 대기중 상태를 나타내는 중간 단계이다. 흰색/검정만 있다면 GC Root에서 발견한 객체를 바로 검정으로 바꿔야 하는데
그 순간 **자식들은 아직 처리 안 했음에도 재방문하지 않게 된다.** 회색이 있어야 Mark Stack에서 꺼내 자식을 처리하는 과정이 명확해지고
알고리즘이 완료됐는지 판단하는 기준이 된다. **회색 객체가 하나도 없을 때** = 마킹 완료라는 종료 조건이 명확해진다.

### Tri-color Invariant가 깨지는 조건 두 가지와 G1GC가 어떻게 방지하는지?
두 조건이 동시에 만족되어야 한다. 첫째, 검정 객체에 흰색 객체로의 새 참조가 추가되어야 하고, 둘째 그 흰색 객체로 가는 모든 회색 경로가 제거되어야 한다.
G1GC는 SATB Write Barrier로 이를 방지한다. 참조가 변경되기 전 값을 SATB큐에 보존해서, 회색 경로가 제거되더라도
Remark 단계에서 재처리한다. 결과적으로 흰색 객체가 살아있는데 수거되는 상황을 방지한다.
